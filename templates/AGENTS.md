# Backlog Operating Guide

Status: active
Audience: LLM agents and humans adding, updating, or closing backlog items
Source of truth: backlog record contract and workflow for this repository

The backlog is a Git-backed JSON pseudo-database: one file per item, one
canonical serialization, validated against `schema.json`. Git history is the
audit log. A read-only hub renders it as HTML/JSON elsewhere; nothing is ever
edited through the hub.

## Layout

```
docs/backlog/
  AGENTS.md         <- this guide
  config.json       <- project settings (areas enum, ...)
  schema.json       <- JSON Schema for items (optional; tool bundles a default)
  done-schema.json  <- JSON Schema for done entries (optional; tool bundles a default)
  index.json        <- GENERATED by `hub.py fmt` - never edit by hand
  feature/          <- new capability, or a product decision unlocking one
  fix/              <- behavior is wrong or incomplete versus documented intent
  rework/           <- restructuring of working behavior: refactor, perf, debt
  security/         <- isolation, hardening, auth, supply chain, security process
  done/             <- completed-work records, one file per outcome
```

## The one workflow rule

Backlog changes are commits to the backlog branch (see `config.json` /
project docs for which branch that is). After ANY edit to files here, run:

```
hub.py fmt --backlog-dir docs/backlog
hub.py validate --backlog-dir docs/backlog
```

`fmt` rewrites files into the canonical JSON form (2-space indent, sorted
keys, trailing newline) and regenerates `index.json`. `validate` must exit 0
before you commit. Non-canonical or invalid files are rejected downstream.

## Item contract

One item = one file at `<type>/<id>.json`. The id encodes type prefix,
creation date, and a slug - no counters, no coordination:

```
FEAT-20260703-salesforce-read-only-sync
^^^^ ^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^
type  YYYYMMDD kebab-case slug
```

Prefixes: `feature`->FEAT, `fix`->FIX, `rework`->RWK, `security`->SEC.
If two branches ever produce the same id, `validate` reports the duplicate
and the fix is renaming one slug.

Fields (full contract in `schema.json`):

- `schema_version`: 1
- `id`, `title`, `type`, `area`, `status` (`open|in-progress|blocked`),
  `priority` (`now|next|later`), `created` (YYYY-MM-DD), `source` (where the
  item came from)
- `risk`: `{level, dimensions[], rollback}` - **mandatory risk assessment**;
  `rollback` is required for `medium` and `high`
- prose as paragraph arrays: `problem`, `value`, `scope`, `validation`,
  optional `trigger`
- `notes`: optional dated entries `{date, text}` for blockers, decision
  state, and updates - never edit history, append a note
- `links`: optional `{prs: [123], related_ids: ["FIX-..."]}`

Write items as actionable outcomes. Never file an item that only says
"improve" or "clean up" without problem, value, and validation.

## Done entry contract

Completed work is recorded as one file per outcome at `done/<id>.json`, with
ids `DONE-YYYYMMDD-slug` (the date part must match the `date` field). Fields
(full contract in `done-schema.json`):

- `schema_version`: 1
- `id`, `date` (YYYY-MM-DD), `title`
- `summary`: paragraph array - what changed and why it is complete
- `validation`: paragraph array - evidence with dates (commands, CI, QA)
- optional: `changed` (files/PRs/branches), `item_id` (the backlog item this
  closes), `item_snapshot` (the closed item's JSON, for full provenance),
  `followup_ids`, `source`

Done entries are append-only history: never edit one after commit except to
fix factual errors. Grouping (by month, by area) is the hub renderer's job -
storage stays one flat file per entry, so there is never a giant log file to
archive.

## When to write what

| You have... | Do this |
| --- | --- |
| A new idea, follow-up, or deferred defect | Add `<type>/<id>.json`, run fmt+validate, commit |
| New information about an existing concern | Append a dated entry to `notes`; update fields if facts changed |
| Work you are about to start | Set `status: in-progress` |
| Something blocking the work | Set `status: blocked` + a note saying what unblocks it |
| Finished work | In ONE commit: delete the item file, add `done/DONE-<date>-<slug>.json` (with `item_id`, optionally `item_snapshot`), run fmt+validate |
| Finished work with no backlog item | Add a done entry without `item_id` |
| An obsolete/wrong item | Delete the file + add a short done entry saying it was dropped and why |
| A decision needing human approval | Keep a `notes` entry `Decision state: proposed`; never mark approved yourself |

The backlog holds OPEN work only. Completed history lives in `done/` and git,
never in item files.

## How to query (for agents)

- All fields are in the JSON records; `index.json` is the fast scan surface
  (id, title, type, area, status, priority, risk_level, path).
- Open security work: read `security/*.json`.
- High-risk work: filter `risk.level == "high"`.
- Pick next work: `status == "open"` and `priority == "now"`, then `next`;
  read the full item (including `trigger`) before starting.
- Item ids are stable reference keys - use them in commits, PRs, and done
  entries.

## Guardrails

- Never edit `index.json` by hand; never skip `fmt` before committing.
- Do not weaken `schema.json` or `config.json` to make an invalid item pass.
- Do not bulk-rewrite items without being asked; keep diffs reviewable.
- Product-scope decisions inside items stay proposed until a human approves
  them.
